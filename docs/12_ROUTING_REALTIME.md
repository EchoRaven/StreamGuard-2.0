# 12 · 升级路由与实时可行性

两条先前缺失的约束。都不是优化项——缺了它们系统会以**不报错的方式**失效。

## 1. 路由按「能力」不按「风险」

先前的设计是 **CUSUM 在风险分上报警 → 升级**，即「看起来危险就上送」。
级联的正确判据是**「低级处理不了就上送」**——能力判据，不是风险判据。

| | 低不确定 | **高不确定** |
| --- | --- | --- |
| 高风险分 | 廉价层判决 | 上送 |
| **低风险分** | 放行 | **必须上送** ← 纯风险路由永远抓不到 |

左下那格正是 sentinel 的盲区（`docs/06 §6.2`）：**它对某类内容没有判别力，
所以分数低——而分数低恰恰是因为它看不懂。**

实测（2000 样本，含 400 个「低分但高 OOD」）：

| 路由方式 | 升级率 | 盲区抓到 |
| --- | --- | --- |
| 纯风险 | 0.05% | **0** |
| 能力 | 13.95% | **228** |

### 二者互补，不是替代

```
CUSUM(风险)   回答「什么时候变了」  —— §3 的延迟界建立在它上面
不确定性       回答「这一条我自己能不能定」 —— 决定要不要花钱
```

CUSUM 报警只是 `route()` 的一项输入（提高 VOI），**不等于上送**。

## 2. 引用门带来的架构约束

sentinel 只产出连续分数，**产不出 `policy_citation`**，而 flag 必须带引用
（`docs/07 §3.2`）。所以：

> **sentinel 不能自己判违规。任何「不安全」判定都必须经中间层。**

后果：**级联只能在否定侧省钱**，肯定侧省不了。升级率的下界就是真实的
不安全率——这直接压低了级联的成本上限。

## 3. 放行必须同时满足「分数低」和「不 OOD」

只看分数是**设计缺陷**：分数低可能是「确实安全」，也可能是
「我没见过所以打不出高分」——后者放行就是漏报。

实测抓到过这个 bug：只按分数判时，分布外帧因相似度低被**大量放行**。
现在 `ood_safe_veto` 否决这类放行。

## 4. 实时可行性：与成本是两条独立约束

> 钱能买更多卡，但**单条流的每一级必须在截止期内完成**，否则积压，
> 而排队延迟要**计入 E[τ−ν]**——系统算不过来造成的延迟，和模型看晚了
> 造成的延迟是同一个量。

三级各自的截止期：

| 层 | 截止期 | 服务时间（实测） | 余量 |
| --- | --- | --- | --- |
| sentinel | 1/f_s = 2000 ms | 21.8 ms | 91.7× |
| 中间层 | 1/(f_s·r) = 40 s | 1526 ms | 26.2× |
| analyst | 1/(f_s·r·q) = 133 s | 8000 ms | 16.7× |

（f_s=0.5fps，r=5%，q=30%）

**采样率把并发能力吃得很快：**

| sentinel | 单卡可并发流数 |
| --- | --- |
| 0.5 fps | 9 |
| 2 fps | 2 |
| 5 fps 以上 | **0**（单条流都撑不住） |

## 5. batching 揭示的事：多流调度不是可选优化

实测 SigLIP2：

| batch | 吞吐 |
| --- | --- |
| 1 | 4.4 帧/秒 |
| 8 | 37.4 帧/秒 |
| 32 | **46.0 帧/秒** |

**10 倍差距。** 但要凑满 batch=32：

```
单流 0.5fps，1 秒窗口内凑满 → 需要 64 条并发流
```

**单条流永远攒不满批，只能跨流攒。**

> ⚠️ 因此 `docs/06 §6.3` 把多流调度「移出范围」的决定是**错的**。
> 它不是排队论的锦上添花，**它是吞吐的前提**。没有跨流批处理，
> sentinel 只能按 4.4 帧/秒算，成本翻十倍。范围应当改回。

## 6. tau 必须标定

⚠️ `CompetenceRouter.tau` 用默认值 0 会让**每一帧都判为「近阈值」**
从而全部上送，升级率 100%——级联完全失效，**且不报任何错**。

`Pipeline.calibrate_router(safe_scores)` 用一批已知安全的分数取 95 分位
作为 tau。未标定时 `run()` 发 `RuntimeWarning`。
